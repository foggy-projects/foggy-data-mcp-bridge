## 2. 结论摘要

当前手册覆盖了主流程 happy path，能够验证 S1 前端元数据接口、成员查询基础能力、直接查询能力、查询实例创建以及 DataViewer 页面基本渲染，但还不够完整，暂时不建议直接作为最终验收手册。

本次复跑后确认：

- 手册中的多数接口步骤可复现，主链路整体可用。
- 手册仍缺少层级成员、异常路径、下载响应头、前端页面控制台/网络错误、分页控件存在性等校验点。
- 手册第 7 步 `query/create` 示例中的排序参数与当前后端实际行为不一致，存在误导风险。
- 页面存在真实问题：前端会请求不存在的 `filter-options` 接口，页面控制台出现 404 与组件注册缺失错误，分页控件也未达到“已验证通过”的标准。

## 3. 手册完整性评估

- `members/query` 的基础查询、关键字查询、已选值回填
- `query/direct/{qmModel}` 的基础查询与多过滤条件查询

- DataViewer 页面基本渲染、筛选控件、汇总行展示

### 3.2 建议补齐内容

建议将以下项目补入手册，否则当前手册更像“主流程演示”，还不能覆盖关键回归点：

1. 层级成员验证
   使用具备层级字段的 QM 进行 `childrenOf`/`descendantsOf` 验证。`FactOrderQueryModel` 本身没有层级字段，不适合承担这部分验证。
2. 下载响应头验证
   除了文件内容，还应明确校验 `Content-Disposition`、文件名、`Content-Type`。
3. 异常路径验证
   至少补充 `qmModel` 为空、`fieldName` 非法、查询实例不存在等失败场景。
4. 前端页面错误检查
   增加浏览器控制台错误、关键网络请求失败的检查，否则“页面打开成功”不能代表组件体系稳定。
5. 分页控件验证
   手册写了“分页可翻页”，但页面当前未看到可用分页器，需单独列为验收项。
6. 排序正确性验证
   需要明确验证 queryId 页面初始排序是否真实生效，而不是仅校验表格能打开。

### 4.2 页面复跑结果

本次实际创建并打开了两组 queryId 页面：

- 手册原始写法：`orderBy: [{ field: "orderTime", order: "desc" }]`
- 修正后写法：`orderBy: [{ field: "orderTime", dir: "DESC" }]`

复核结果：

- 两个页面都能打开并渲染表格、筛选器和汇总行。
- 使用手册原始写法时，首行时间并未表现为最新时间，排序结果不符合“倒序”预期。
- 使用 `dir: "DESC"` 后，首行数据为 `2025-12-31`，倒序行为符合预期。

结论：手册第 8 步所依赖的第 7 步 `query/create` 示例参数需要修订，否则用户按文档执行时可能得到“页面能打开，但排序不对”的结果。

## 5. 补做抽查结果

### 5.2 异常路径补充验证

对 `members/query` 发送缺少 `qmModel` 的请求，返回：

- `code=600`
- `exCode=B600`
- `msg=qmModel 不能为空`

说明：后端失败场景已有返回规范，手册应至少补 1 到 2 个负向用例。

### 5.3 层级成员能力补充验证

`FactOrderQueryModel` 的 frontend-meta 中没有层级字段，`hierarchicalFieldCount=0`，因此不能验证 `childrenOf`。

为确认真实能力，本次改用 `FactTeamSalesQueryModel` 额外抽查：

- `frontend-meta` 中存在层级字段 `team$id`
- `members/query` 的 `childrenOf("T001")` 可返回子节点
- `descendantsOf("T001")` 可返回后代节点

结论：后端具备层级查询能力，但手册选错了示例模型，导致层级能力没有被覆盖。

## 6. 本次发现的问题

### 6.1 手册示例排序参数与当前实现不一致

手册 `query/create` 示例使用：

```json
{
  "orderBy": [
    { "field": "orderTime", "order": "desc" }
  ]
}
```

但本次实际复核显示，当前后端/页面链路只有在使用 `dir: "DESC"` 时，页面初始排序结果才符合预期。

影响：

- 按手册执行时，用户可能误认为排序已经验证通过。
- 实际上只是页面成功打开，排序语义未真正落地。

建议：

- 将手册示例调整为与当前后端实际兼容的排序字段。
- 或者在实现层统一兼容 `order` 与 `dir` 两种写法。

### 6.2 前端调用了不存在的 `filter-options` 接口

页面打开后，浏览器网络请求出现：

- `/data-viewer/api/query/FactOrderQueryModel/{queryId}/filter-options/customer%24caption`

该请求返回 404，页面控制台进一步报出 `Failed to load filter options: Error: 查询不存在`。

影响：

- 筛选组件的远程选项加载存在真实缺口。
- 当前页面即使看起来能渲染，也不能认定筛选链路完全通过。

### 6.3 页面存在组件注册缺失/运行期告警

页面控制台还出现以下错误或警告：

- `vxe-tooltip` 未注册
- `vxe-pager` 未注册
- `[vxe table] 不支持的参数 "show-overflow=true"...`

影响：

- 这说明标准组件页面仍有运行时集成问题。
- 手册目前没有要求检查这些问题，容易把“可见页面”误判为“可验收页面”。

### 6.4 分页验收项与当前页面状态不一致

手册写明应验证“分页可翻页”，但本次页面中未见可正常使用的分页器。

影响：

- 当前这项不能视为已验证通过。
- 建议手册把“分页器存在且可切页”拆成单独的显式检查点。

### 6.5 层级响应元数据仍不完整

虽然 `FactTeamSalesQueryModel` 的 `childrenOf`、`descendantsOf` 已能工作，但成员查询响应中未体现清晰的层级元信息，当前前端很难据此稳定构建树形选择体验。

这不阻塞本次“主链路复跑”结论，但属于后续应跟进的问题。

## 7. 建议对手册的最小修订

建议至少补齐以下 6 条，使其达到“可复核、可回归”的标准：

1. 在现有步骤后追加“异常路径验证”小节。
2. 在下载步骤中明确校验响应头与文件名。
3. 将层级成员验证改为使用具备层级字段的 QM 模型。
4. 在 DataViewer 页面验证中新增“控制台无 4xx/5xx/组件缺失错误”检查。
5. 将“分页可翻页”改为实际点击验证，而不是观察式描述。
6. 修正 `query/create` 排序参数示例，并增加“首行数据确为最新时间”的断言。

本次复跑结论为：
