## 基本信息

- 阶段：`阶段2：统一接入 QueryFacade 主链`
- 负责人：`Codex`

## 本阶段核心改动
- 在 `QueryModelLoaderImpl` 增加 synthetic member-QM 运行时识别与装载逻辑。
- 新增 `SyntheticMemberQueryModelFactory`，把阶段1解析出的 schema 构造成可执行的运行时 `JdbcQueryModelImpl`。
- 将 `JdbcServiceImpl.queryDimensionData` 从旧 `queryDimensionDataByHierarchy` 旁路切到：
  - `model + fieldName -> SyntheticMemberQueryModelDescriptor`
  - `synthetic model name -> QueryFacade.queryModelData`
- 修复 `SyntheticMemberQueryModelResolver` 的 schema 全局字段列表未聚合问题，避免运行时模型拿到空 schema。
- 补充 `SyntheticMemberQueryModelRuntimeTest` 与 `SyntheticMemberQueryModelResolverTest`，覆盖运行时装载、simple 入口归一、字段边界与 SQL 生成。

## 关键设计决策
- synthetic member-QM 继续采用“运行时虚拟 QueryModel”方案，不新增物理 `.qm` 文件。
- 装载入口放在 `QueryModelLoaderImpl.getJdbcQueryModel(...)` 内部，命中 `${qmName}#${dimFieldBase}` 后先解析原 QM，再由 factory 构造 synthetic runtime QM。
- simple 入口不再自己拼维度 SQL，而是统一转换为 `DbQueryRequestDef`，直接进入 `QueryFacade` 主链。
- synthetic member-QM 的 root query object 绑定到根维度自身，而不是原 fact QM 根节点，确保成员查询不回退为“按事实数据裁剪成员”。

## 遇到的问题与处理
- 问题：synthetic member-QM 运行时 `getJdbcQueryColumns()` 为空，导致 `id/caption` 不可查询。
- 根因：`SyntheticMemberQueryModelResolver` 只把字段塞进 node 局部列表和 `fieldIndex`，没有写入 schema 的全局 `fields`。
- 处理：补上 `state.fields.add(field)`，随后 Stage2 运行时模型可正常拿到 schema 并注册查询列。

- 问题：仓库默认启用 `multi-db` profile，执行 `mvn -Dtest=... test` 时会触发第二个 surefire execution（`test-postgres`），该轮会对指定测试类出现 `ClassNotFoundException`。
- 处理：阶段性验证命令统一使用 `-P !multi-db`，只保留单次 surefire 执行；该问题属于现有构建配置与 `-Dtest` 的交互，不属于 synthetic member-QM 实现缺陷。

## 结果判断
- Stage2 核心目标已达成：
  - synthetic member-QM 可被 loader 运行时装载；
  - simple 入口已归一到 QueryFacade 主链；
  - DSL 可直接用 synthetic model 名进入同一执行模型；
  - 新主路径不再依赖旧成员旁路作为核心执行链。
