## 本阶段目标

- 让 synthetic member-QM 可被 `QueryModelLoader` 识别并运行时装载
- 让 simple 入口归一到 synthetic model 后走 `QueryFacade`
- 让 DSL 入口可直接使用 `${qmName}#${dimFieldBase}`
- 让新主路径不再依赖旧维度成员旁路作为核心执行链

## 关键实现点

### 1. synthetic member-QM 装载入口

- 在 `QueryModelLoaderImpl.getJdbcQueryModel(...)` 中增加 synthetic 名称识别
- 当模型名包含 `#` 时，先回溯源 QM，再通过 `SyntheticMemberQueryModelResolver` 生成 descriptor
- 由 `SyntheticMemberQueryModelFactory` 在运行时构建可执行的 `JdbcQueryModelImpl`
- 构建后的 synthetic model 直接注册进现有 namespace cache

### 2. 运行时 builder 的执行根

- synthetic member-QM 的 `DbTableModel` 不再以 fact root 为根
- root 直接切到目标维度自己的 `QueryObject`
- 根维度下的嵌套子维度 join graph 重新拼装
- 这样 `buildSqlOnly` 输出的 SQL 会直接落到维表及其维度子树，而不是事实表

### 3. canonical 列注册修复

- 运行时 builder 会创建 canonical `id/caption` 等列
- 现有 `QueryModelSupport.addJdbcQueryColumn(...)` 之前对 dimension 列有一条过早返回逻辑
- 这会导致 synthetic builder 自定义出来的 dimension 语义列没有真正进入 `dbQueryColumns`
- 本阶段改为：
  - 仅对标准 caption 维度列补嵌套别名注册
  - 自定义列继续走统一的直接注册逻辑
  - 同名同底层列重复注册时跳过，而不是报错

### 4. simple 入口归一

- `JdbcServiceImpl.queryDimensionData(...)` 不再直接依赖旧的 `queryDimensionDataByHierarchy(...)`
- 先用 resolver 把 `model + fieldName` 解析成 synthetic member-QM descriptor
- 再构造 `DbQueryRequestDef`，统一走 `QueryFacade.queryModelData(...)`
- simple 入口返回值只保留当前阶段所需的 canonical `id/caption`

## 关键设计取舍

- 本阶段不展开 hierarchy operator 语义，只确保运行时 builder 与主链打通
- 旧旁路暂时保留代码形态，但新主路径不再把它当核心依赖
- 不在阶段2处理外部权限 patch；等阶段4再做

## 遇到的问题

### 问题1：synthetic model 缺少 canonical `id`

- 表现：`buildSqlOnly` / runtime test 报 synthetic model 找不到 `id`
- 原因：`addJdbcQueryColumn(...)` 会丢弃 synthetic builder 创建的自定义 dimension 列
- 结论：通过最小修复列注册逻辑解决，不改 stage1 schema 规则

### 问题2：运行时 builder 是否真的落到维表 root

- 通过 runtime test 验证 `FactSalesNestedDimQueryModel#product` 的 SQL root 已指向 `dim_product_nested`
- 并能自动带上 `dim_category_nested` 的子维 join
