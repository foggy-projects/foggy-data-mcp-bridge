# v9.x 多维透视语义层：全盘复盘与业界对比报告

在完成了 9.x (Pivot Semantic Layer) 的核心战役推演后，本报告将退后一步，以全局视角对目标合理性进行论证、盘点设计中潜在的缺漏，并前瞻性地对比业界主流 BI 系统。

---

## 一、 目标的合理性与解决问题的价值评估

**核心目标：** 将底层引擎的表达力从“关系型表格 (Tabular)”跨越到“多维坐标系 (Multi-Dimensional)”，同时保持输入层极度的 LLM 友好性。

**价值合理性评估：** 极度合理且必要。
1.  **突破“大宽表”的业务幻象**：现代商业分析（如中国式财务报表、门店日销追踪）本质是网格化的。如果仅仅停留在 8.x 的扁平模式或依靠 `compose_script` 强行拼接，系统在应对“稀疏补全”、“动态小计”时会遇到极高的计算复杂度和 LLM 幻觉墙。
2.  **LLM 驱动的下一代 BI 范式**：当前 AI 数据分析的最大痛点是“大模型不懂 SQL 的隐式关系”。9.x 将轴 (Axes)、度量 (Metrics)、属性 (Properties) 显式分离，这完全契合了 LLM 的思维结构，使得自然语言转报表的准确率将产生质的飞跃。

---

## 二、 深度复盘：当前设计的潜在缺漏与盲区

尽管流水线设计非常优雅，但从工程落地的角度审视，9.x 架构依然存在以下需要防范的盲区：

### 1. 盲区一：透视表的“后置列计算” (Inter-Column Calculations)
*   **痛点：** 目前的 `calculatedFields` 是在聚合期间计算的（基于行数据）。但在透视表中，业务人员经常需要增加一列**“差异列”**（例如：列 A 是 2023 年，列 B 是 2024 年，用户要求追加一列算 B - A）。
*   **改进策略（二次加工）：** 不必在 Pivot DSL 中强行发明复杂的后置语法。如果遇到后置计算，直接利用现有的 CTE 编排能力 (`compose_script`)，用中间变量接收 Pivot 的输出结果并在内存中或引擎侧挂载简单的 Formula Hook 进行二次加工。

### 2. 盲区二：引擎内存爆炸的风险 (OOM Risk)
*   **痛点：** 战役二中，我们将骨架补全 (CrossJoin) 和小计 (Subtotal) 提到了 Java/Python 引擎的内存中处理。如果前端发起了一个极高基数维度的透视（例如：行轴是 100 万个客户 ID，列轴是 365 天），引擎在做内存笛卡尔积时会瞬间 OOM。
*   **改进策略（硬性熔断）：** 这是所有非预计算的物理瓶颈。无论是交由引擎层还是推入 SQL 层，都无法避免。必须在引擎层强制引入**“基数熔断器 (Cardinality Circuit Breaker)”**，一旦预测格子数超限，直接实施硬性拦截并报错。

### 3. 盲区三：`timeWindow` 在多维模型中的冲突与水土不服
*   **痛点：** 8.x 的 `timeWindow` (如 YOY, MOM) 默认会生成 `sales__prior` 等扁平的新列。但在 Pivot 模式下，这种横向摊平行为会与列轴（Columns）自身的空间展开行为发生严重的语义和结构冲突，成为不必要的负担。
*   **改进策略（功能互斥禁用）：** 明确在进入 `pivot` 模式时，**直接禁用并拒绝 `timeWindow` 语法**。Pivot 模式下的同环比计算应当统一收束到使用 `OFFSET` 等行/列级坐标偏移函数来实现，避免能力叠加造成的混乱。

## 三、 v9.x 落地后与业界主流 BI/语义层的横向对比

一旦 Foggy v9.x 架构完全实现，它在业界将处于一个非常独特且具有碾压性优势的生态位。

### 1. 对比传统重量级 OLAP (如 Mondrian / SSAS / Kylin)
*   **业界现状：** 强依赖提前建 Cube（物化视图），MDX 语法极度复杂，更改一个维度的属性需要重新跑批刷数据。
*   **Foggy 9.x 优势：** 
    *   **彻底的动态性**：Level 和 Property 在查询时由 LLM 动态解耦，无需建 Cube。
    *   **零侵入的 DSL**：没有晦涩的 MDX 语法，纯 JSON 协议驱动。

### 2. 对比现代 Headless BI (如 Cube.dev / MetricFlow)
*   **业界现状：** Cube.dev 堪称目前的标杆，但它的 JSON 查询不支持真正的 `Properties` 隔离（导致底层 GROUP BY 爆炸），且强制要求客户端 SDK 在前端 JS 中完成小计和透视。
*   **Foggy 9.x 优势：**
    *   **性能代差**：通过显式解耦附属属性并使用智能伪聚合/Post-Join，底层 SQL 执行效率远超 Cube.dev。
    *   **全栈适配**：小计和骨架生成由后端引擎包揽，输出多模态自适应结构（全模态契约），无论下游是轻量级小程序还是重型 Web 看板都能完美接入。

### 3. 对比桌面端霸主 (如 Tableau / PowerBI)
*   **业界现状：** 拥有最完美的透视操作体验和 DAX/VizQL 语言，但属于封闭生态，且 DAX 对 LLM 极度不友好。
*   **Foggy 9.x 优势：**
    *   **LLM Native（大模型原生）**：Foggy 9.x 本质上是**为 AI 智能体打造的 PowerBI 引擎**。它剔除了隐式上下文陷阱，用最清晰的三元结构（Row/Col/Metric）让 LLM 能够毫无障碍地生成专业级交叉报表。

### 4. 对比传统开源可视化基座 (如 Superset / Metabase)
*   **业界现状：** 本质是 SQL 拼接器。它们的“透视表”仅仅是前端 UI 层面对扁平 SQL 结果的一层包装，遇到稀疏数据（缺少某个月份）根本无力解决。
*   **Foggy 9.x 优势：**
    *   具备真正的多维语义引擎，能够在后端完美实现 **CrossJoin 骨架补全**，保证了财报级的数据严谨性。

---
**总结陈词：**
Foggy v9.x 的架构设计绝非“重复造轮子”，而是敏锐地捕捉到了 **“LLM 时代的数据基座不该是 DAX，也不该是生硬的 SQL”** 这一行业空白。通过吸收 MDX 的空间坐标系思想，并以轻量级的 AST 降维编译（避开重量级依赖），Foggy 将成为极具竞争力的现代化智能语义引擎。
