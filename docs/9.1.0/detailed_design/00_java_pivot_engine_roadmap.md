# Java Pivot Engine 9.1.0 Roadmap

## 1. Background

9.0.0.beta Java Core has been signed off with risks. The accepted release boundary includes:

- SQL TopN/Having pushdown through managed queryModel relation.
- Non-additive subtotal/grandTotal alignment with surviving TopN domain.
- MySQL 5.7 guarded memory fallback.
- `domain > 500` fail-closed for non-additive subtotal/grandTotal.
- Cascade Generate, advanced tree SQL, and outer Pivot cache deferred.

The purpose of 9.1.0 is to move deliberate future capabilities out of 9.0.0 release risk and into a planned roadmap.

## 2. Guiding Rules

- Do not change the public Pivot DSL unless a separate requirement explicitly approves it.
- Do not bypass queryModel; permission, preAgg, physical column checks, params, logging, and sanitizer behavior remain mandatory.
- Treat Stage 5A and Stage 5B as separate tracks.
- Prefer telemetry-driven implementation over speculative complexity.
- Keep unsupported advanced MDX semantics rejected by default.

## 3. Track A: Release Hardening and Observability

### A1. CI Release Readiness

Goal: make 9.0.0 release readiness repeatable in CI.

Scope:

- Wire `scripts/verify-pivot-v9-release.ps1` / `.sh` into CI.
- Provide MySQL8 and PostgreSQL service containers or documented CI profiles.
- Keep SQLite fast path for PR checks.

Acceptance:

- CI can run Pivot Java Core parity on SQLite.
- Scheduled or release-gated CI can run MySQL8 and PostgreSQL parity.
- Failure output points to the failing profile and test class.

### A2. Pushdown and Fallback Telemetry

Goal: decide Stage 5A with real usage evidence.

Metrics/log markers:

- SQL pushdown attempted / succeeded / fallback.
- Fallback reason: dialect, unsupported metric, tree mode, parentShare/baselineRatio, permission, planner refusal.
- `NonAdditiveRollupDomainTooLargeException` count and domain size.
- Non-additive auxiliary query count and duration.
- Generated domain transport candidate size where available.

Acceptance:

- Release logs can answer whether `domain > 500` is common.
- Telemetry does not expose sensitive SQL values.

## 4. Track B: Stage 5A Large-Domain Transport

Goal: replace unsafe oversized `IN` / `OR-of-AND` predicates with an internal joinable domain relation when needed.

Current 9.0.0 behavior:

- `domain > 500` fails closed.
- Stage 5A spike result: No-Go for 9.0.0.beta; defer to 9.1.0.

9.1.0 proposed design:

- Add internal `DomainTransportPlan`.
- Add dialect SPI such as `DomainRelationRenderer`.
- Start with a fail-closed default implementation.
- Evaluate:
  - `VALUES` CTE for PostgreSQL/SQLite where syntax is clean;
  - `UNION ALL` derived table as a portable fallback;
  - temp/session table only if telemetry proves very large domains are common.

Required tests:

- tuple correlation;
- null-safe tuple matching;
- `preAgg + systemSlice + domain transport + non-additive subtotal`;
- base params before/after domain params as generated by final SQL shape;
- dialect capability refusal;
- MySQL8/PostgreSQL parity;
- MySQL5.7 fallback or derived-table decision.

Non-goals:

- no public DSL option;
- no default-on behavior until acceptance;
- no cascade Generate implementation.

## 5. Track C: Stage 5B Cascade Generate and Multi-Level TopN

Goal: define correct semantics for multiple axis fields with `limit`.

Current issue:

- Current supported subset covers single-level / controlled per-group TopN.
- Multiple axis fields with simultaneous `limit` can rank at the wrong grain if intermediate aggregation is not explicit.

Design questions:

- Does each level rank by current-level aggregate or descendant-subtree aggregate?
- Does TopN apply before or after axis Having at each level?
- How are ties ordered deterministically?
- How do surviving uneven domains interact with CrossJoin and subtotal?
- Can SQL pushdown express each level as staged CTEs without exploding query size?

Acceptance before implementation:

- SQL oracle examples for at least two-level TopN.
- Explicit mismatch cases showing why old memory behavior is insufficient.
- Guardrails for ambiguous requests.
- C1.1 LLM-safe disambiguation accepted, including C2 whitelist, explicit fail-closed cases, rewriteable errors, and a ban on current memory fallback for cascade requests.
- `13_pivot_stage5b_c2_implementation_plan.md` created to map semantics to an execution pipeline and test matrix.
- C2 v1 rows two-level cascade implementation accepted with risks after oracle/refusal tests, quality gate, coverage audit, and feature acceptance signoff.
- C2 behavior outside the accepted v1 subset remains fail-closed: SQL Server, conservative MySQL 5.7, tree mode, cross-axis cascade, three-level cascade, having-only cascade, and non-additive cascade totals are rejected/deferred.

## 6. Track D: Tree Advanced Semantics

Goal: evaluate tree SQL TopN and tree subtotal support.

Current 9.0.0 behavior:

- `hierarchyMode=tree` is rows-only.
- `tree + crossjoin` is rejected.
- `tree + subtotals` is rejected because parent nodes already act as subtotal-like aggregates.

Candidate 9.1.0 work:

- Evaluate closure-table or descendant-enumeration strategy for tree TopN.
- Decide whether `expandDepth` is display-only or filter semantics.
- Define whether non-additive tree rollup uses descendant auxiliary queries.

Recommendation:

- Keep this behind design only until Stage 5B ranking semantics are stable.

## 7. Track E: Outer Pivot Cache

Goal: evaluate caching after SQL pushdown without reusing invalid inner query cache semantics.

Open questions:

- Cache key must include Pivot DSL, managed relation metadata, preAgg state, systemSlice, permission context, dialect, and pushdown plan.
- Inner query cache must not short-circuit before outer Pivot SQL runs.
- Cache invalidation must align with existing queryModel / preAgg cache rules.

Recommendation:

- Do not start before telemetry identifies repeated expensive Pivot queries.

## 8. Not Planned Unless Reopened

- Public `CELL_AT`.
- Public `AXIS_MEMBER`.
- Public `ROLLUP_TO` function strings.
- Arbitrary MDX set algebra.
- QueryModel bypass for Pivot-specific SQL.

These remain outside 9.1.0 default scope.
