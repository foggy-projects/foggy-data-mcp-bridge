# Pivot Stage 5B: Cascade Generate Semantics

## 1. Purpose
This document defines the strict semantic rules for "Cascade Generate" (multi-level TopN and Having) in the Pivot engine. It resolves ambiguities regarding ranking grain, tie-breaking, having-order, cross-axis interactions, and subtotal behaviors to ensure a deterministic, SQL-pushdown-friendly implementation for `PIVOT-91-C2`.

## 2. Goals and Non-Goals
**Goals**:
- Freeze the semantic contract for multi-level axis limits.
- Guarantee deterministic output regardless of memory vs. SQL pushdown execution.
- Maintain queryModel lifecycle security (no arbitrary SQL generation bypassing queryModel).
- Define concrete bounds for what is accepted vs. rejected (Fail-Closed).

**Non-Goals**:
- Immediate implementation in Java (this is purely design).
- Modifying the public Pivot API/DSL syntax.
- Supporting arbitrary MDX set algebra.

## 3. Current Accepted 9.0.0.beta Behavior
In 9.0.0.beta, the Pivot engine:
- Supports single-level TopN or controlled TopN via SQL pushdown (`PivotAxisDomainSqlPlanner`).
- Executes axis Having before TopN at the same level.
- Rejects complex multi-level TopN requests where semantics are ambiguous, falling back to memory processing which may rank at the wrong grain if not explicitly controlled.
- Evaluates TopN over the `_base_relation` independent of the opposite axis (row limits ignore column limits).

## 4. Terminology
- **Axis Level**: A single dimension field in the `rows` or `columns` array.
- **Current-Level Aggregate**: The aggregation of a metric grouped by all axis fields up to and including the current level.
- **Descendant/Subtree Aggregate**: The aggregation of a metric computed only from the explicitly surviving leaf nodes of the subtree.
- **Surviving Domain**: The set of dimension members that remain after all Having and TopN filters are applied.
- **Uneven Domain**: A scenario where parent nodes have differing numbers of surviving children (e.g., Region A has 3 categories, Region B has 1 category).
- **Cascade Generate**: The iterative application of TopN/Having from the outermost level to the innermost level, where each level's filter domain is restricted by its parent's surviving domain.

## 5. Proposed Semantic Decision
We propose a **conservative, predictable default** for Stage 5B:

1. **Ranking Grain**: Multi-level TopN ranks each level by the aggregate at that level **after** parent-domain filtering. (It ranks by Current-Level Aggregate, not descendant-subtree aggregate).
2. **Having Order**: Axis Having is always applied **before** TopN at the same level.
3. **Tie-Breaking**: Ties are ordered deterministically by the requested order metric, followed by an explicit NULL bucket and the stable axis key in ASC order. Do not rely on dialect default NULL ordering.
4. **Uneven Domains**: Uneven surviving domains are allowed **only** when generated by explicit staged parent-child ranking. Arbitrary simultaneous multi-level limits without staged semantics remain rejected.
5. **Subtotal/GrandTotal**: Must aggregate **only over the surviving domain**, not the full original domain.
6. **Non-Additive Limitations**: Non-additive subtotal with multi-level TopN remains **gated** until SQL oracle and parity tests exist.
7. **Dialect Feasibility**: If semantics cannot be expressed with staged CTEs while preserving the `queryModel` lifecycle, the engine must **fail closed**.

## 6. Ranking Grain Rules
For a request with `rows: [{field: "region", limit: 2}, {field: "category", limit: 3}]`:
- Level 1 (`region`): Ranks regions by the sum of metrics across all categories.
- Level 2 (`category`): Within each *surviving* region, ranks categories by the sum of metrics across all leaf data for that `(region, category)`.
- It does **not** rank regions based on the sum of only their top 3 categories.

## 7. Axis Having Order Rules
At any given level `L`, if both `having` and `limit` are specified:
1. Aggregate at level `L` for the parent's surviving domain.
2. Apply `having` filters (e.g., `sales > 1000`).
3. Rank the remaining tuples.
4. Apply `limit`.

## 8. Deterministic Tie-Breaking Rules
TopN pushdown MUST include a deterministic tie-breaker to prevent pagination or cross-database inconsistency.
- Primary Order: Defined by `AxisField.orderBy` (e.g., `SUM(sales) DESC`).
- Tie-Breaker: an explicit NULL bucket followed by the current level's dimension key in `ASC` order, for example `CASE WHEN category IS NULL THEN 1 ELSE 0 END ASC, category ASC`.
- NULL values in the dimension key must be handled explicitly across dialects. The default C1 rule is NULLS LAST for ASC tie keys unless a future accepted product rule changes it.

## 9. Row Axis vs Column Axis Behavior (CrossJoin)
Row limits and Column limits are evaluated **independently** over the base relation.
- Row TopN computes its aggregates across all columns.
- Column TopN computes its aggregates across all rows.
- The final grid is the Cartesian product (CrossJoin) of the Surviving Row Domain and Surviving Column Domain, left-joined with the base facts.
- **Why**: Evaluating Row TopN *after* Column TopN would make the row ranking dependent on column limits, violating commutativity and causing severe SQL generation explosion.

## 10. Subtotal/GrandTotal Interaction
Subtotals and GrandTotals must reflect the **visual total** of the surviving grid.
- They are computed by aggregating over the Cartesian product of the Surviving Domains.
- They must **not** include data from regions or categories that were filtered out by TopN or Having.

## 11. Non-Additive Metric Limitations
If a non-additive metric (e.g., `COUNT_DISTINCT`, `AVG`) is used with subtotals AND multi-level TopN:
- **Gated / Rejected**: The system currently cannot easily push down surviving-domain subquery constraints for non-additive metrics in a performant way across all dialects. It must `fail-closed` rather than returning incorrect approximations.

## 12. Dialect/Pushdown Feasibility
These semantics can be achieved via Staged CTEs:
- `_base_relation`: Original queryModel SQL.
- `_level1_domain`: Group by Level 1, Having, Rank, Limit.
- `_level2_domain`: Inner join `_base_relation` with `_level1_domain`, Group by Level 1 & 2, Having, Rank, Limit.
- `_surviving_domain`: Inner join all levels.

If a dialect lacks Window Functions and the request is **single-level** TopN only, it may fall back to memory execution. If memory execution risks memory exhaustion (e.g., domain > 500), it fails closed.

> **C1.1 Supersession (cascade requests)**: For Cascade Generate / multi-level TopN requests, memory fallback is **forbidden** regardless of dialect capability. C1.1 (`12_pivot_stage5b_cascade_generate_disambiguation.md`) requires that cascade requests execute only through a verified staged SQL path. Current memory execution lacks staged parent-domain filtering and cannot guarantee correct ranking grain. A future staged memory implementation may be reconsidered only if it has its own parity oracle coverage equivalent to the SQL oracle matrix.

## 13. Rejected or Gated Request Shapes
- **Simultaneous Row and Column Multi-Level TopN**: If semantics become ambiguous or CTE generation explodes beyond dialect limits.
- **Tree Hierarchy with TopN**: Gated until Track D (Tree Advanced Semantics) is resolved.
- **Non-additive Subtotals with Multi-level TopN**: Rejected explicitly.

## 14. SQL Oracle Examples

### Case 1: Single-Level TopN Baseline
```sql
WITH _base_relation AS (
  SELECT region, category, sales FROM base_table
),
_row_domain_1 AS (
  SELECT region, SUM(sales) AS _agg_sales
  FROM _base_relation
  GROUP BY region
),
_row_ranked_1 AS (
  SELECT region, ROW_NUMBER() OVER (ORDER BY _agg_sales DESC, region ASC) AS rn
  FROM _row_domain_1
),
_filtered_1 AS (
  SELECT region FROM _row_ranked_1 WHERE rn <= 2
)
SELECT b.*
FROM _base_relation b
INNER JOIN _filtered_1 f1
  ON (b.region = f1.region OR (b.region IS NULL AND f1.region IS NULL))
```

### Case 2: Two-Level Row Axis TopN & Case 5: Uneven Domain
`region limit 2`, then within each region `category limit 3`.
```sql
WITH _base_relation AS (
  -- queryModel base
  SELECT region, category, sales FROM base_table
),
-- Level 1: Region
_row_domain_1 AS (
  SELECT region, SUM(sales) AS _agg_sales
  FROM _base_relation
  GROUP BY region
),
_row_ranked_1 AS (
  SELECT region,
         ROW_NUMBER() OVER (
           ORDER BY _agg_sales DESC,
                    CASE WHEN region IS NULL THEN 1 ELSE 0 END ASC,
                    region ASC
         ) AS rn
  FROM _row_domain_1
),
_filtered_1 AS (
  SELECT region FROM _row_ranked_1 WHERE rn <= 2
),
-- Level 2: Category (Restricted by Level 1)
_row_domain_2 AS (
  SELECT b.region, b.category, SUM(b.sales) AS _agg_sales
  FROM _base_relation b
  INNER JOIN _filtered_1 f1
    ON (b.region = f1.region OR (b.region IS NULL AND f1.region IS NULL))
  GROUP BY b.region, b.category
),
_row_ranked_2 AS (
  SELECT region,
         category,
         ROW_NUMBER() OVER (
           PARTITION BY region
           ORDER BY _agg_sales DESC,
                    CASE WHEN category IS NULL THEN 1 ELSE 0 END ASC,
                    category ASC
         ) AS rn
  FROM _row_domain_2
),
_filtered_2 AS (
  SELECT region, category FROM _row_ranked_2 WHERE rn <= 3
)
-- Final
SELECT b.*
FROM _base_relation b
INNER JOIN _filtered_2 f2
  ON (b.region = f2.region OR (b.region IS NULL AND f2.region IS NULL))
 AND (b.category = f2.category OR (b.category IS NULL AND f2.category IS NULL))
```

### Case 3: Axis Having Before TopN
`category sales > 1000`, then `limit 3`.
```sql
WITH _base_relation AS ( ... ),
_row_domain_1 AS (
  SELECT category, SUM(sales) AS _agg_sales
  FROM _base_relation
  GROUP BY category
),
_row_having_1 AS (
  SELECT * FROM _row_domain_1 WHERE _agg_sales > 1000
),
_row_ranked_1 AS (
  SELECT category,
         ROW_NUMBER() OVER (
           ORDER BY _agg_sales DESC,
                    CASE WHEN category IS NULL THEN 1 ELSE 0 END ASC,
                    category ASC
         ) AS rn
  FROM _row_having_1
),
_filtered_1 AS (
  SELECT category FROM _row_ranked_1 WHERE rn <= 3
)
...
```

### Case 4: Deterministic Tie Case
Ensured by `ORDER BY _agg_sales DESC, CASE WHEN category IS NULL THEN 1 ELSE 0 END ASC, category ASC`. This avoids relying on dialect default NULL ordering.

### Case 6: Subtotal/GrandTotal Surviving-Domain Case
If Row Subtotals are requested on the 2-level TopN grid:
```sql
-- Using the _filtered_2 from Case 2
WITH _surviving_facts AS (
  SELECT b.region, b.category, b.sales
  FROM _base_relation b
  INNER JOIN _filtered_2 f2
    ON (b.region = f2.region OR (b.region IS NULL AND f2.region IS NULL))
   AND (b.category = f2.category OR (b.category IS NULL AND f2.category IS NULL))
)
-- Grand Total
SELECT 'TOTAL' AS region, 'TOTAL' AS category, SUM(sales) FROM _surviving_facts
UNION ALL
-- Subtotal Level 1
SELECT region, 'TOTAL' AS category, SUM(sales) FROM _surviving_facts GROUP BY region
UNION ALL
-- Leaf Level
SELECT region, category, SUM(sales) FROM _surviving_facts GROUP BY region, category
```

### Case 8: Non-Additive Metric Gated Case
`COUNT_DISTINCT(user_id)` with multi-level limits + subtotals.
If pushed down, the subtotal requires `COUNT(DISTINCT user_id)` over `_surviving_facts`. However, `_surviving_facts` involves joins that might explode grain if not perfectly aligned, or if memory fallback is used, we cannot recalculate distinct counts without raw data. **Decision: Rejected**.

## 15. Mismatch Cases (Why Old Behavior is Unsafe)
In 9.0.0.beta memory fallback, multi-level TopN was processed by retrieving ALL data for the outer limits, sorting in Java, and truncating. Without explicit staged filtering (Level 2 limits being evaluated *after* Level 1 limits), the Java memory path might rank Level 2 globally across all regions, or run out of memory for high cardinality dimensions before the TopN could be applied.

Furthermore, `PivotAxisDomainSqlPlanner` currently evaluates `_row_domain_2` against the **unfiltered** `_base_relation`. This means Level 2 ranking is global (ignoring Level 1 survival), which can result in a Level 1 region returning 0 categories if all its categories ranked poorly globally! The proposed semantics specifically introduce `INNER JOIN _filtered_1` inside `_row_domain_2` to solve this.

## 16. C2 Implementation Gates
Before PIVOT-91-C2 (Implementation) can begin:
1. `PIVOT-91-C1` design must be formally accepted by the architecture board.
2. Dialect matrix must confirm `ROW_NUMBER() OVER (PARTITION BY ...)` support across all target engines.
3. Telemetry must show a need for Cascade Generate to justify the CTE complexity overhead.
