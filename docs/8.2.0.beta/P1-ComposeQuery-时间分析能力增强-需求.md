## 背景

8.2.0.beta 完成 `QueryPlan` 主语义后，Foggy 在固定 schema 下的业务分析能力会显著补齐：

- 二段聚合
- `JOIN` 后再查
- `UNION` 后再查
- TopN / limit / distinct 后继续分析
- 中间关系复用

但根据既有能力评估，Foggy 在 L3 高级分析层仍存在明显短板，主要集中在：

- 窗口函数尚未成为 `QueryPlan` 主语义
- 缺少时间偏移与同比环比
- 缺少 `MTD` / `QTD` / `YTD` 等区间累计
- 缺少连续时间轴补齐

这些能力若长期缺失，Foggy 在“明细查询 + 分析查询”混合场景下虽然足够做 L1 / L2，但仍难以覆盖经营分析、财务分析、运营看板中的高频时间问题。

## 前提与依赖

本需求默认建立在以下前提之上：

- `QueryPlan` / 派生查询 / `JOIN` / `UNION` 主语义已经稳定
- 阶段切断与当前阶段字段可见性规则已经冻结
- `execute()` / `toSql()` 与权限托底链路已经可用
- 当前版本不以“开放任意 SQL 逃生口”作为时间分析主路径

说明：

- 时间粒度分桶本身不是本需求的主要难点。Foggy 的 TM / QM 体系通常可以通过补充 `year` / `quarter` / `month` / `day` 等属性支持基础分桶。
- 本需求的重点是“时间分析语义”，而不是“如何生成时间字段”。

## 目标

- 在 `QueryPlan` 主语义层正式纳入时间分析能力，而不是把时间分析留给自由 SQL 片段
- 补齐经营分析高频的时间比较与累计能力
- 让 AI 与分析师能够以受控、稳定的 DSL 表达时间趋势分析
- 尽量复用既有阶段切断、字段引用对象、派生查询心智，不引入第二套完全不同的时间 DSL

## 非目标

- 不追求 100% 覆盖 SQL 全部时间函数
- 不在本需求中一并补齐 `WHERE EXISTS` / 相关子查询 / 递归 CTE / `INTERSECT` / `EXCEPT`
- 不把“任意 SQL 时间表达式拼装”作为推荐主路径
- 不在第一批范围中引入复杂 cohort / retention 全家桶 DSL
- 不在本需求中定义完整的财务会计日历体系；若后续需要，单独立项

## 能力范围

本需求建议分四层推进。

### 1. 窗口分析

这是第一优先级。

最低应覆盖：

- `row_number`
- `rank`
- `dense_rank`
- `lag`
- `lead`
- `sum() over (...)`
- `avg() over (...)`

目标效果：

- 支持排名类分析
- 支持累计值
- 支持滚动均值
- 为同比 / 环比提供基础能力

### 2. 时间偏移与时间比较

这是第二优先级。

最低应覆盖：

- 前 1 期 / 前 N 期
- 同比
- 环比
- 差值
- 增长率

目标效果：

- 支持经营分析中的月同比、月环比、周环比、季同比等常见问题
- 不要求用户手工拼接时间维 Join

### 3. 区间累计

这是第三优先级。

最低应覆盖：

- `MTD`
- `QTD`
- `YTD`
- rolling 7 / 30 / 90

目标效果：

- 支持财务、销售、运营看板中的累计到当期问题
- 让“期间累计”进入主语义层

### 4. 连续时间轴补齐

这是第四优先级。

最低应覆盖：

- 缺失日期补齐
- 缺失月份补齐
- 补齐后再参与同比 / 环比 / 窗口分析

目标效果：

- 避免图表断点
- 避免同比与滚动计算因为空桶而失真

## 核心语义约束

### 1. 必须服从既有阶段切断规则

时间分析能力进入 `QueryPlan` 后，仍必须服从：

- `.select()` 创建新阶段
- 新阶段只能看到当前投影列
- 窗口列、比较列、累计列一旦生成，也只是当前阶段的新输出列

不得为了时间分析绕过现有可见性规则。

### 2. 必须是主语义，不是 SQL 字符串逃生

允许底层编译成 SQL 窗口函数或方言时间表达式，但对上暴露时：

- 应优先提供对象化、显式的 DSL
- 不应要求分析师或 AI 手工写 `DATE_TRUNC` / `LAG(...) OVER (...)` 一类字符串表达式

### 3. 时间比较应尽量显式

同比、环比、前期比较等能力，如果最终通过窗口函数编译实现，也应尽量在 DSL 层体现为显式语义，而不是要求用户自行拼接：

- “当前值”
- “前值”
- “差值”
- “增长率”

### 4. 尽量复用 TM / QM 已有时间维字段

若 TM / QM 已提供稳定的年月日等属性：

- DSL 层不应重复造完整的时间分桶体系
- 更适合把重点放在“比较、累计、窗口、补齐”这些高价值分析语义上

## 推荐设计方向

本需求不锁死最终 API，但建议遵守以下设计方向：

- 时间粒度语义由时间字段或时间维对象承载
- 窗口、偏移、比较、累计语义由聚合列或分析列承载
- 结果仍然通过 `.select(...)` 输出，进入后续派生阶段继续使用

> [!NOTE]
> **关于单 DSL 查询 vs 底层 QueryPlan 抽象的架构关系**
> 
> 针对 AI 生成查询，应提供高度声明式、意图驱动的 **Single Query DSL**（单查询 DSL），例如：
> ```json
> {
>   "timeWindow": { "comparison": "yoy", "grain": "month" }
> }
> ```
> 这种高层 DSL 对 AI 极度友好，认知负荷低且不涉及底层 SQL 细节。
> 
> 而本需求（**QueryPlan 窗口主语义化**）是引擎底层的 **执行机制层 (Mechanism)**。上层的 Single Query DSL 解析器在识别到 `yoy` 意图后，将自动调用底层的 `.lag().over(...)` API 构建 AST 节点。两者架构分层明确、完美互补。

推荐避免的方向：

- 大量依赖字符串 SQL 函数
- 让分析师自己拼日历表 Join
- 在一个版本里同时引入过多概念，导致 DSL 激增

## 验收标准

如果本需求进入实现阶段，至少应满足以下验收口径：

1. 能在 `QueryPlan` 语义层表达排名、前值、累计、同比或环比中的核心子集
2. 新增语义生成的字段能够进入后续派生阶段继续引用
3. 不因引入时间分析而破坏既有 `JOIN` / `UNION` / 派生查询语义
4. AI 在固定 schema 与元数据可发现前提下，能稳定生成主流时间分析查询，而无需频繁退回自由 SQL
5. 参考手册中能给出“推荐写法”和“非推荐写法”，尤其要覆盖：
   - 累计值
   - 同比 / 环比
   - 补零 / 补桶
6. 至少提供一组覆盖经营分析常见问题的集成测试样例，例如：
   - 月销售额趋势
   - 月同比 / 月环比
   - TopN 客户累计消费
   - rolling 30 days

## 预期收益

若本需求完成，预期收益包括：

- Foggy 在固定 schema 下的业务分析覆盖度可由当前约 `72% - 82%` 提升到约 `80% - 88%`
- Foggy 在时间趋势分析、排名、累计、同比环比等场景下显著缩小与 Cube 的差距
- Foggy 保持“关系节点可编排”的既有优势，同时补齐最关键的一块高级分析短板
- AI 生成查询的稳定性提升，因为不再需要自行发明窗口 SQL 或时间 Join

## 风险与约束

- 若一次性引入过多时间 DSL，可能导致语义系统膨胀
- 若高度依赖底层数据库方言细节，可能造成 Java / Python 两端或多方言编译结果漂移
- 若把大量能力继续放在字符串表达式里，时间分析会重新退回“伪 DSL + SQL 片段”的状态
- 若先补窗口而不补时间比较与补桶，业务价值会提升，但仍不足以明显改善财务和经营看板体验

## 建议实施顺序

建议按以下顺序推进：

1. 窗口函数主语义化
2. 时间偏移、同比环比
3. `MTD` / `QTD` / `YTD` 与 rolling window
4. 连续时间轴补齐

这个顺序的理由是：

- 先补基础分析算子
- 再补高频业务语义
- 最后补图表与时序连续性体验
