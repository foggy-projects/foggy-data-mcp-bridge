# P1-Compose Query 时间分析能力增强评估

## 文档作用

- doc_type: evaluation
- intended_for: design-review / product-decision / execution-agent
- purpose: 在既有 `QueryPlan` / 派生查询 / `JOIN` / `UNION` 语义基础上，评估 Foggy 后续补齐时间分析能力的可行边界、优先级与预期收益，为 8.3.0 及后续版本的语义扩展提供决策依据

## 结论先行

结论分三点：

1. 在当前 `QueryPlan` 语义基础上，**可以继续补齐时间分析能力**，且补法应当是“增加一等时间语义”，而不是“开放任意 SQL 时间表达式”。
2. 不必追求覆盖全部 SQL 时间函数。只要补齐经营分析和 BI 报表里最常见的一组能力，整体业务分析覆盖度就能显著提升。
3. 如果补齐窗口函数、时间偏移、同比环比、累计区间等核心能力，Foggy 在固定 schema 下的业务分析覆盖度有机会从当前文档评估的 `72% - 82%`，进一步提升到约 `80% - 88%`；但若不补 `EXISTS` / 相关子查询 / 更完整集合运算，仍不应宣称接近完整 SQL。

## 评估前提

### 1. 本文只讨论“时间分析语义”，不重复讨论通用关系能力

默认前提：

- `QueryPlan` 派生查询、阶段切断、`JOIN`、`UNION` 已经成立
- `execute()` / `toSql()` 等执行与编译链路已经可用
- 同数据源下的派生关系复用成立

因此，本文不重复展开：

- 二段聚合
- `JOIN` / `UNION` 基础语义
- 通用权限托底
- SQL 编译框架

### 2. 不以“100% 达到 SQL 能力”为目标

本文目标不是把 Foggy 变成 SQL 方言镜像层，而是：

- 在现有 DSL 上补齐高频时间分析场景
- 提高分析师与 AI 的稳定使用率
- 避免把复杂时间逻辑重新退回自由 SQL

### 3. 时间粒度分桶不是本文的主难点

在 Foggy 的 TM/QM 建模体系下，时间维度通常可以通过增加 `year` / `quarter` / `month` / `day` 等派生属性进行补齐。因此：

- “能否按月/按季聚合”本身不是最大难点
- 真正的难点在于：
  - 时间窗口
  - 前后期偏移
  - 同比 / 环比
  - MTD / QTD / YTD
  - 连续时间轴补齐

换言之，Foggy 当前更缺的是“时间分析语义层”，而不是“时间桶字段本身”。

## 当前能力缺口

根据 [P0-Compose Query 固定 Schema 下业务分析能力对比评估](D:/foggy-projects/foggy-data-mcp/foggy-data-mcp-bridge-wt-dev-compose/docs/8.2.0.beta/P0-ComposeQuery-固定Schema下业务分析能力对比评估.md) 的结论，Foggy 在 L1 / L2 已较强，但在 L3 高级分析仍明显落后，核心原因集中在：

- 缺少正式纳入 `QueryPlan` 主语义层的窗口函数体系
- 缺少显式的时间偏移语义
- 缺少 period-to-date 一类区间累计语义
- 缺少连续时间桶补齐能力
- 时间比较主要仍需依赖手工建模或后续手工拼接

这些缺口并不要求一次性补成“完整 SQL 能力”，但如果长期缺失，会直接限制：

- 销售趋势分析
- 财务同比 / 环比
- 运营看板滚动窗口
- 排名与分层分析
- 时间序列异常检测前置查询

## 应补齐的能力分层

为避免把需求做散，建议把时间分析能力分成 4 层。

### T1：时间维规范化

这层能力的目标是让“按什么粒度看时间”成为稳定语义。

典型需求：

- 按日 / 周 / 月 / 季 / 年聚合
- 明确时间字段的展示粒度
- 在后续阶段中可继续引用对应时间列

对 Foggy 而言，这层更多是：

- 统一字段命名与引用方式
- 统一时间粒度列的生成规则
- 不要求一定由 DSL 动态生成，也可主要依赖 TM / QM 预建字段

判断：

- T1 重要，但不是最紧急短板
- 如 TM 已能提供稳定时间属性，T1 可以只做轻量语义封装

### T2：窗口分析

这层是时间分析的第一关键层。

建议优先纳入：

- `row_number`
- `rank`
- `dense_rank`
- `lag`
- `lead`
- `running total`
- `moving average`

这层能力会直接决定 Foggy 能否从“能做组合报表”升级为“能做常见分析看板”。

### T3：时间比较

这层是经营分析高频能力。

建议优先纳入：

- 上期 / 前 N 期比较
- 同比（YoY）
- 环比（MoM / QoQ / WoW）
- 差值与增长率

这类能力不要求用户自己写日历表 Join，也不宜要求用户手工写 `lag(...) / current - prev / prev` 组合。

### T4：区间累计与时间轴补齐

这层更贴近 BI 与财务场景。

建议优先纳入：

- `MTD`
- `QTD`
- `YTD`
- 滚动 7 / 30 / 90 天
- 连续时间桶补零 / 补齐

这部分若不做，很多图表虽然“查得出来”，但趋势线、同比口径和空桶表现会很差。

## 与现有 QueryPlan 语义的衔接方式

### 1. 不建议退回字符串 SQL 表达式主导

不建议将时间分析能力主要设计成：

- `select("DATE_TRUNC(...) as month")`
- `select("LAG(totalAmount) OVER (...) as prevAmount")`
- `select("SUM(...) OVER (...) as runningTotal")`

原因：

- AI 难以稳定生成
- 方言差异会放大
- 错误定位会退回“SQL 片段错误”
- 与现有 `FieldRef` / `QueryPlan` 一等语义方向相冲突

### 2. 更适合继续走“对象化 + 显式语义”路线

当前 `FieldRef` 已支持：

- `.sum()`
- `.count()`
- `.avg()`
- `.max()`
- `.min()`

因此时间分析能力更适合继续扩展为：

- 时间字段侧：表达“按何种粒度看时间”
- 聚合字段侧：表达“如何在时间顺序上比较与累计”

推荐原则：

- 粒度语义靠时间字段或时间维对象承载
- 比较 / 累计 / 排名语义靠聚合列或窗口对象承载
- 结果仍然是当前阶段的投影列，继续遵守阶段切断规则

### 3. 推荐两级设计，而不是一个万能 API

推荐分成两级：

1. 时间维级语义
   - 负责“时间轴如何组织”
   - 例如：日、月、季、财务期、补桶
2. 分析列级语义
   - 负责“在时间轴上如何比较与累计”
   - 例如：`lag`、累计、同比、环比、滚动均值

这样更符合现有 `QueryPlan -> select -> derived stage` 的心智，也更适合 AI 约束输出。

## 推荐能力清单

建议按以下顺序评估和补齐。

### P1：窗口函数进入 QueryPlan 主语义层

这是第一优先级。

建议至少纳入：

- `row_number`
- `rank`
- `dense_rank`
- `lag`
- `lead`
- `sum() over (...)`
- `avg() over (...)`

收益：

- 排名类分析可进入主路径
- 累计值和滚动均值有了一等语义
- 为同比 / 环比 / 时间偏移打下基础

### P2：时间偏移与同比环比

这是第二优先级。

建议补齐：

- 前一周期
- 前 N 周期
- 同比
- 环比
- 差值
- 增长率

收益：

- 销售趋势、财务对比、经营看板覆盖度明显提升
- 这是 Foggy 追近 Cube 时间分析能力的关键一步

### P3：区间累计

建议补齐：

- `MTD`
- `QTD`
- `YTD`
- rolling 7 / 30 / 90

收益：

- 财务和经营类看板基本盘补齐
- 多数“累计到当期”问题不再需要手工窗口 SQL

### P4：连续时间轴补齐

建议补齐：

- 缺失日期 / 月份补零
- 补齐后再做窗口与对比

收益：

- 解决“图表断点”“同比空值”“滚动窗口缺口”问题
- 使时间分析结果更适合直接用于图表层

## 不建议本期一并追求的能力

以下能力有价值，但不建议与第一批时间分析语义同时推进：

- 全量数据库日期函数映射
- 任意 interval algebra
- 递归时间序列生成
- 复杂 cohort / retention 全家桶 DSL
- 与所有数据库方言逐一对齐的时间表达式兼容层

原因：

- 会显著推高 DSL 复杂度
- 会弱化“显式语义”方向
- 会让 AI 和分析师重新退回 SQL 心智

## 对业务分析覆盖度的预估影响

在当前评估基线下：

- 仅完成 `QueryPlan` / 派生查询 / `JOIN` / `UNION`，业务分析覆盖度约 `72% - 82%`
- 若再把窗口函数和时间比较纳入主语义，预计可抬升到约 `80% - 88%`

需要强调：

- 这不是“接近完整 SQL”
- 这也不意味着超越 Cube 在时间分析上的全部积累
- 但在“固定 schema + 明细与分析混合 + AI 生成查询”这条主路径上，Foggy 的实用能力会明显增强

## 相对 Cube / Looker 的位置变化

若完成本文建议中的 P1 ~ P3：

- Foggy 在“明细查询 + 组合分析”上仍会保持自身优势
- Foggy 在“时间趋势 / 排名 / 同比环比”上会显著缩小与 Cube 的差距
- Foggy 仍不应声称拥有 Looker 那种“SQL-based derived table 全兜底”路线

更准确的判断应是：

- Foggy 强于“关系节点可编排”
- Cube 强于“时间与指标分析体系化”
- Looker 强于“derived table + SQL 逃生口”

补齐时间分析后，Foggy 会从“L2 很强、L3 偏弱”提升为“L2 很强、L3 进入可用区间”。

## 设计约束建议

后续若把本文升格为正式需求，建议明确以下约束：

1. 时间分析能力必须走 `QueryPlan` 主语义层，不以自由 SQL 字符串为主路径
2. 新增能力必须继续服从“阶段切断”和“当前阶段字段可见性”规则
3. 时间比较语义要尽量显式，不要求分析师或 AI 自己发明日历 Join
4. 尽量避免在一个版本里同时引入过多概念，优先补“窗口 + 对比 + 累计”三件最值钱的能力
5. 如 TM 已能稳定暴露年月日等属性，则 DSL 层不必重复造完整时间桶体系

## 后续评估问题清单

本文建议在正式立项前，重点评估以下问题：

1. 时间粒度字段主要依赖 TM 预建，还是 DSL 提供轻量封装入口
2. 窗口函数能力是否以 `FieldRef.over(...)` 为主入口
3. 同比 / 环比是设计成显式高层语义，还是基于 `lag/lead` 做语法糖
4. 连续时间桶补齐是否进入 QueryPlan 主语义，还是先由图表层兜底
5. 财务期间 / 自定义会计日历是否作为第一批范围

## 建议结论

建议把“时间分析能力增强”作为 `P1` 级后续演进方向单独立项，且优先级明确低于：

- 8.2.0.beta 当前 `QueryPlan` 主线闭环
- 现有权限 / 编译 / 脚本链路的稳定收口

但在 `QueryPlan` 主线稳定后，时间分析是最值得优先补齐的一块高级语义空白。

如果只允许补一轮能力，建议顺序为：

1. 窗口函数主语义化
2. 时间偏移、同比环比
3. MTD / QTD / YTD 与 rolling window
4. 连续时间轴补齐

这个顺序能够在不追求完整 SQL 的前提下，最大化业务分析收益。
